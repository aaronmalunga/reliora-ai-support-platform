# 1. Purpose

`routing-intent-v1` is a controlled benchmark dataset for evaluating Reliora's top-level customer-request router.

The prediction task is single-label classification into exactly one of:

```text
BUG
PLATFORM
OTHER
```

The dataset supports the routing experiment documented in:

```text
experiments/routing/README.md
```

It is intended to help evaluate routing alternatives before Reliora selects a preferred runtime routing strategy.

---

# 2. Requirements Traceability

The dataset supports:

```text
FR-004 — Intent Classification
ADR-002 — Separate intent classification from knowledge coverage
ADR-012 — Benchmark routing alternatives before selecting the production routing strategy
```

It does not evaluate the separate knowledge-coverage decision from FR-005.

Therefore labels such as:

```text
PLATFORM_SUPPORTED
PLATFORM_UNSUPPORTED
```

must not appear in this dataset.

---

# 3. Evidence Classification

The customer messages in version 1 are deliberately designed benchmark fixtures.

They are not represented as production customer traffic.

Fixture provenance:

```text
SYNTHETIC ASSUMPTION
```

Results generated by executing models against the versioned dataset may be classified as:

```text
EXPERIMENTAL
```

This distinction must be preserved in reports and portfolio claims.

---

# 4. Dataset Size Target

Version 1 targets:

```text
180 total messages
45 semantic families
3 balanced intent classes
4 message variants per family
```

Class target:

```text
BUG        60
PLATFORM   60
OTHER      60
```

Family target:

```text
BUG        15
PLATFORM   15
OTHER      15
```

---

# 5. Semantic Family

A semantic family represents one underlying customer scenario.

Example:

```text
family_id:
bug-checkout-crash

intent:
BUG
```

Possible variants:

```text
Checkout crashes when I click Pay.

The payment page closes whenever I try to finish my order.

I cannot complete checkout because the app freezes.

Every time I press the payment button the page crashes.
```

These are different messages but represent the same underlying scenario.

Semantic families exist primarily to reduce train/test leakage.

---

# 6. Family-Aware Splitting

All variants belonging to the same semantic family must remain in the same dataset split.

This is prohibited:

```text
checkout-crash variant 1 → train
checkout-crash variant 2 → test
```

because the test example would be too closely related to data already observed during training.

The required rule is:

```text
semantic family
      ↓
one split only
      ↓
train OR validation OR test
```

---

# 7. Planned Split

Per intent class:

```text
9 families → train

3 families → test
```

Because every family contains four message variants:

```text

9 families

9 families
```

Overall:


Each split remains balanced across:

```text

```

---

# 8. Why the Test Set Is Family-Held-Out

The final test set should contain scenarios not represented by sibling paraphrases in training.

This provides a stronger question than:

> Can the classifier recognize another wording of a scenario it already saw?

Instead, the test asks more closely:

> Can the classifier generalize the intent definition to held-out semantic scenarios?

This still does not establish production generalization because the dataset is synthetic.

Identifies the underlying semantic scenario.




# 11. BUG Label Policy

A message should receive `BUG` when its primary purpose is to report an apparent technical malfunction.

Examples of semantic areas may include:

```text
checkout crash
login failure
page freeze
button malfunction
upload failure
incorrect UI behaviour
search malfunction
notification defect
cart malfunction
mobile application crash
```

A BUG example should describe something behaving incorrectly rather than simply asking how a feature is supposed to work.

---

# 12. PLATFORM Label Policy

A message should receive `PLATFORM` when its primary purpose is requesting information about the platform, its products, supported workflows, services, or policies.

Potential semantic areas include:

```text
return policy
shipping times
payment methods
account settings
order changes
warranty information
loyalty program
student discount
supported countries
product availability
```

Whether Reliora currently possesses enough approved knowledge to answer the question is irrelevant to this label.

A platform question remains:

```text
PLATFORM
```

even when later knowledge coverage becomes:

```text
UNSUPPORTED
```

---

# 13. OTHER Label Policy

A message should receive `OTHER` when its primary purpose is outside both:

```text
technical bug reporting
and
platform-information requests
```

Potential areas may include:

```text
unrelated general knowledge
creative-writing requests
personal advice
external-company questions
unsupported tasks
off-domain requests
```

`OTHER` must not become a fallback label for PLATFORM requests whose answer is unknown.

---

# 14. Boundary Cases

The dataset should intentionally contain difficult boundary cases.

Examples:

```text
"Is checkout supposed to freeze for a few seconds?"
```

This sounds like a question but reports apparent malfunction.

Likely intent:

```text
BUG
```

Another example:

```text
"What happens if my payment fails?"
```

This may be a policy/workflow question rather than a report that the customer's payment actually failed.

Likely intent:

```text
PLATFORM
```

The label must follow the customer's communicative intent, not merely isolated keywords such as:

```text
crash
error
payment
refund
```

---

# 15. Lexical-Overlap Cases

Some cases should deliberately contain vocabulary commonly associated with another class.

Examples:

```text
PLATFORM message mentioning "error"
OTHER message mentioning "order"
BUG message phrased as a question
```

This helps determine whether a classifier learns useful intent distinctions rather than simple keyword shortcuts.

---

# 16. Message Variation

Version 1 should include controlled variation such as:

```text
formal wording
informal wording
short messages
longer descriptions
questions
statements
minor spelling errors
abbreviations
polite requests
frustrated wording
technical wording
non-technical wording
```

Variation should remain realistic rather than adding arbitrary noise simply to make the dataset look difficult.

---

# 17. Multi-Issue Messages

Some messages may mention more than one issue.

However, version 1 remains a single-label routing dataset.

Such cases require a reviewed dominant-intent rule.

If the dominant intent cannot be determined consistently, the case should not be silently forced into a label merely to preserve dataset size.

Ambiguous cases should be:

```text
reviewed
rewritten
or excluded
```

until an explicit ambiguity policy exists.

---

# 18. Class Balance

Version 1 intentionally uses equal class counts:

```text
BUG        60
PLATFORM   60
OTHER      60
```

This is a benchmark design choice.

It does not claim that real customer traffic contains equal intent frequencies.

Production class distribution remains unknown unless measured evidence establishes it.

---

# 19. Synthetic Balance vs Production Frequency

The balanced class distribution exists to make candidate comparison and per-class analysis clearer.

Therefore:

```text
benchmark class frequency
≠
production class frequency
```

No operational-volume inference should be made from the dataset.

---

# 20. Dataset Leakage Risks

Potential leakage sources include:

```text
near-identical paraphrases across splits
template prefixes
class-specific formatting patterns
case identifiers exposed as features
family identifiers exposed as features
split metadata exposed as features
systematic wording differences created by dataset generation
```

Only the customer `message` should normally be used as model input.

Metadata fields exist for experiment governance and analysis.

---

# 21. Split Integrity Validation

Before training, automated validation should verify:

```text
every case ID is unique

every family belongs to exactly one split

every family has exactly one expected intent

only BUG / PLATFORM / OTHER labels exist

only train / validation / test splits exist

class counts match the dataset specification

family counts match the dataset specification

required fields are populated
```

The benchmark should fail before model training if these integrity conditions are violated.

---

# 22. Test-Set Discipline

The test set is final held-out evidence for a benchmark version.

During model development:

```text
train
→ model fitting

validation
→ candidate comparison / tuning

test
→ final evaluation
```

The test set should not be repeatedly used to guide feature engineering or hyperparameter choices.

If test cases materially influence model development, a new held-out version may be required for stronger subsequent evidence.

---

# 23. Dataset Review

Before benchmark execution, the dataset should be reviewed for:

```text
label consistency
ambiguous intent
duplicate wording
family leakage
unrealistic examples
class artifacts
incorrect split assignment
```

Automated validation is necessary but cannot establish that every semantic label is correct.

Human review remains part of dataset governance.

# 26. What This Dataset Can Support

With appropriate execution evidence, the dataset can support statements such as:

> Candidate A achieved a macro F1 of X on the held-out split of `routing-intent-v1` under the documented benchmark configuration.

It cannot by itself support statements such as:

```text
Candidate A achieves X accuracy in production.

The dataset represents real customer traffic.

The router is production-ready.

The model generalizes to all customer requests.
```
